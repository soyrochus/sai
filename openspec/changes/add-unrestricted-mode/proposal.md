## Why

SAI restricts generated commands to a whitelist of configured tools. That is the right default, but it has no escape hatch: when the task genuinely needs a tool the config does not list, or a combination of tools, there is no way to get it in one invocation. `--unsafe` does not help — it relaxes operator blocking only and still enforces the whitelist, so the model remains constrained to the same tools.

The failure is quiet rather than loud, which is what makes it worth fixing. Asked to show Rust items from recently changed files, SAI returned only `find . -type f -name '*.rs' -mmin -30 -print` — the half of the job its whitelist permitted. The user gets a plausible, incomplete command with no indication that a restriction shaped it.

## What Changes

- Add `--unrestricted`, which lifts the tool whitelist and operator blocking for a single invocation and executes through the shell.
- **The whitelist is lifted in two places, not one.** The system prompt built in [src/prompt.rs](src/prompt.rs) instructs the model that it may use *only* the configured tools; validation in [src/safety.rs](src/safety.rs) then enforces it. Relaxing validation alone leaves the flag inert, because the model would still emit only whitelisted tools.
- Make inspection mandatory and non-suppressible in this mode: an explanation is always produced, and the confirmation requires typing `yes` in full. A bare `y`, which clears every other confirmation in SAI, does not clear this one.
- Add `safety.allow_unrestricted` to the global config, defaulting to true. When false, `--unrestricted` refuses to run and names the config file that forbade it.
- Record unrestricted invocations distinctly in the execution history log so `--analyze` and later auditing can identify them.
- No change to any existing default. Every current invocation behaves exactly as it does today.

### Decisions carried from clarification

- **Name**: `--unrestricted`, describing what it lifts rather than implying recklessness, and leaving `--unsafe` its narrower operator-level meaning.
- **Confirmation strength**: mandatory explanation plus a typed `yes`. The extra keystrokes are the point — this is the mode where a wrong command is unbounded, so muscle-memory `y` should not clear it.
- **Config gate**: `safety.allow_unrestricted: false` disables the mode outright, so a shared or managed machine can keep its whitelist meaningful.

### Known limitation, stated deliberately

The forced explanation is generated by **the same model that produced the command**. It is not an independent check: a destructive command can receive a calm, plausible explanation. Forced explain buys legibility, not verification. The compensating control is a locally computed risk summary (SPEC-04's preflight card), which has no model in the loop; this proposal specifies the deterministic risk markers that `--unrestricted` needs and leaves the full card to its own change.

## Capabilities

### New Capabilities

- `command-safety`: The layered controls between a generated command and its execution — tool restriction, operator blocking, explanation, confirmation, and the flags and configuration that select between them. Introduced here because `--unrestricted` is only meaningful relative to the layers it lifts, and those layers have never been specified.

### Modified Capabilities

_None. `prompt-input` and `prompt-history` are unaffected: this change alters what happens to a command after generation, not how the prompt is obtained._

## Impact

- **Code**: [src/cli.rs](src/cli.rs) gains the flag; [src/prompt.rs](src/prompt.rs) gains an unrestricted system-prompt variant; [src/safety.rs](src/safety.rs) makes the whitelist check conditional and gains local risk markers; [src/app.rs](src/app.rs) gains a strict confirmation path and the config gate; [src/config.rs](src/config.rs) gains a `safety` section; [src/history.rs](src/history.rs) gains a field on `HistoryEntry`.
- **Flag interaction**: `--unrestricted` implies `--unsafe` and `--explain` rather than conflicting with them; `--no-explain`-style suppression must not exist for this mode.
- **Compatibility**: `HistoryEntry` gains a field, so it must default when absent to keep existing `history.log` files readable by `--analyze`.
- **Product boundary**: unchanged. This remains natural language to one reviewed command, not a REPL or script interpreter. The whitelist stops being *the* control and becomes the default, with the human as the control when it is lifted.
- **Docs**: a new `sai help unrestricted` topic, plus README and the existing `unsafe` topic, which currently states the whitelist is always enforced and would become wrong.
